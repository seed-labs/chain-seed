# Ethereum PoS、Clique PoA 与 Monero PoW 的时钟跳变行为

本文从修改内核时间开始，说明客户端怎样感知变化、共识规则怎样受到影响，以及为什么恢复时间后仍可能停块。结论对应本次使用的 Lighthouse v7.0.1、Geth v1.10.26（Clique）和 Monero v0.18.3.3，不能直接推广到所有版本。

先明确三个区别：**修改时间起点不等于加快时间流速；恢复系统时间不等于恢复客户端内部状态；进程还在运行不等于链还在出块。**

## 实验配置

实验于 2026 年 10 月在 WSL Linux 环境进行，使用 Docker Engine 29.9.0。调时影响同一内核下的全部实验节点。

| 实验 | 客户端与拓扑 | 时间参数 |
| --- | --- | --- |
| Ethereum PoS | Lighthouse v7.0.1；每 slot 12 秒 | 独立进行短时及 3 小时跳变，包含保持与恢复阶段；不与下两组视为相同观测窗口 |
| Ethereum PoA | Geth v1.10.26-stable-e5eb32ac；3 个 Clique 签名者、1 个观察节点；周期 15 秒 | 自动难度 Monero 对照中的基线、保持偏移及恢复观察各 300 秒 |
| Monero PoW | Monero v0.18.3.3-release；新建 testnet；1 个单线程矿工、1 个同步节点，使用自动难度；当前协议阶段目标间隔为 60 秒 | 每组新建链并预热到至少高度 65；基线、保持偏移及恢复观察各 300 秒，约每 10 秒采样 |

正式比较包含 −30、+30、−10800、+10800 秒四组偏移。PoA 和 Monero 分别位于独立局域网，不依赖跨 AS 转发。保持期间暂停 NTP 与 Hyper-V 隐式校时，使用单调时钟计量实际持续时间，并在结束后恢复实时时钟与原校时配置。

下文区分实测结果、协议规则与根据源码推断的长期行为；未进行永久保持偏移的长期验证。

## 1. 实验到底改变了什么

### 1.1 修改的是内核 CLOCK_REALTIME

实验通过 Python 的以下调用修改系统时钟：

```python
time.clock_settime(time.CLOCK_REALTIME, target)
```

Python 通过系统接口设置 Linux 内核维护的实时时钟。这与用 `date` 设置系统时间属于同一类操作：改变系统提供的当前时间，而非用 `LD_PRELOAD` 拦截某个进程的读时函数，再返回一个伪造偏移。我们没有加载 faketime。

| 时钟 | 表示什么 | 本次调时会怎样 |
| --- | --- | --- |
| `CLOCK_REALTIME` | 从 Unix Epoch 起计算的日期和时间 | 被直接向前或向后设置 |
| `CLOCK_MONOTONIC` | 单调经过时间，常用于持续时间测量 | 不随这次实时时钟设置直接跳变 |

同一 Linux 内核下的普通 Docker 容器共享实时时钟。本实验给临时辅助容器授予调时权限，修改的是当前 WSL Linux 环境的时间，因此所有相关容器一起受到影响；不是只给某个链节点设置一个独立时钟。

读时间也不意味着每次都必须陷入内核：Linux 可以通过 vDSO 提供读取结果，但读到的仍是内核维护的时钟。[Linux 时钟接口说明](https://man7.org/linux/man-pages/man2/clock_settime.2.html)区分了这些时钟及设置实时时钟对计时器的影响。

### 1.2 跳变之后，时间仍按正常速度走

假设未调时的参考时间在实验开始时为 `12:00:00`：

| 操作 | 刚调完 | 实际再经过 120 秒 | 恢复后 |
| --- | --- | --- | --- |
| 回拨 30 秒 | 11:59:30 | 12:01:30 | 12:02:00 |
| 调快 30 秒 | 12:00:30 | 12:02:30 | 12:02:00 |
| 回拨 3 小时 | 09:00:00 | 09:02:00 | 12:02:00 |
| 调快 3 小时 | 15:00:00 | 15:02:00 | 12:02:00 |

这里每个实际秒仍对应一个时钟秒。我们改变的是偏移，不是让链以更高倍速运行，也没有提高 CPU 执行速度。

脚本用初始锚点记录实时时间 `R0` 和单调时间 `M0`，之后计算：

```text
未调时的参考时间 R = R0 + (当前单调时间 − M0)
保持偏移时的目标时间 = R + 偏移量
恢复时的目标时间 = R
```

因此恢复不会把时间设置回实验开始的 `12:00:00`，而是回到考虑了真实经过时间的 `12:02:00`。实验期间暂停自动校时，结束后恢复原来的校时配置，避免 NTP 或 Hyper-V 在保持期抵消偏移。

### 1.3 为什么恢复后还会出现问题

恢复只设置内核时间，不会撤销已经接受的区块、清除已签名职责记录、重建所有候选模板，或重新计算所有定时器。

两个方向分别包含两次跳变：

```text
回拨实验：先向后跳 → 保持偏移并正常走时 → 恢复时向前跳
调快实验：先向前跳 → 保持偏移并正常走时 → 恢复时向后跳
```

还需要区别“重新读取当前日期”与“此前已经开始等待一段时长”。例如，客户端根据当时的墙钟计算出要等待 3 小时，再创建持续时间计时器。后来把墙钟恢复，并不必然取消这个等待。具体行为必须看客户端使用的时钟与调度代码。

## 2. Ethereum PoS：时间决定当前 slot，slot 决定职责

### 2.1 从内核时间到验证者工作

Lighthouse 的 `SystemTimeSlotClock::now()` 通过 `SystemTime::now()` 获取当前实时时间，再由 `slot_of()` 换算 slot：

```text
当前 slot = 创世 slot + floor((当前实时时间 − 创世时间) / 每 slot 时长)
```

本例每 slot 为 12 秒。Beacon 节点和验证者据此判断现在应处理哪个 slot 的区块、证明和其他职责：

```text
CLOCK_REALTIME 改变
  → SystemTime 读到新时间
  → 当前 slot 改变
  → 调度的职责、消息时效判断及链状态处理发生变化
```

源码见 [SystemTimeSlotClock](https://github.com/sigp/lighthouse/blob/v7.0.1/common/slot_clock/src/system_time_slot_clock.rs) 的 `now()`、[slot 换算实现](https://github.com/sigp/lighthouse/blob/v7.0.1/common/slot_clock/src/manual_slot_clock.rs) 的 `slot_of()`。跨 slot 的状态处理见 [Ethereum 共识规范](https://ethereum.github.io/consensus-specs/specs/phase0/beacon-chain/)的 `process_slots()`。

### 2.2 回拨 30 秒：重回已经处理过的职责时间

假设节点已完成 slot 100～102 的相关工作，回拨 30 秒后，当前 slot 可能重新落到 100 附近。链头和签名记录不会跟着倒退，于是客户端可能重新请求已经处理过的职责，或发现当前 slot 落后于链头。

签名保护会拒绝重复或冲突请求。日志中的 `SameData` 表示重复请求被拒绝，**不表示已经签出了冲突签名，更不表示已经发生可罚没的双签**。

你的理解“保持 120 秒，其中约 30 秒属于重复时间，后面约 90 秒又进入新的时间范围”在时钟层面成立。时间会正常向前走，越过原先处理过的 slot 后，有机会继续新职责。但是否立即恢复，还取决于调度、链头与共识状态，不能单凭超过 30 秒作保证。

如果保持期内已经恢复工作，再恢复系统时间，相当于突然向前跳 30 秒：会跳过约 2～3 个 slot 的机会。已经错过的 slot 不会补出，之后可能继续正常职责。

### 2.3 调快：slot 跳号，执行层区块高度仍连续

向前 30 秒通常跨过约 2～3 个 slot，向前 3 小时约跨过 900 个 slot。一个简化例子是：

```text
调时前：slot 100，执行层高度 80
调快后：slot 1000，执行层高度 81
下一块：slot 1001，执行层高度 82
```

跳过的是按时间定义的 slot；执行层区块编号仍按父块加一。空缺 slot 没有对应区块，节点还需处理跨过的 slot、epoch 及相关状态。

此前本地调快 3 小时的日志中，slot 从个位数跳到约 906～915，执行层高度仍从 5 连续推进到 15。这说明保持偏移的短期内可以出块，不能据此证明最终性、投票和奖惩均无影响。

恢复时是向后跳 3 小时。日志出现当前 slot 约 27、已知链头 slot 915，以及 `SlotTooLow`：恢复后的时钟已经落后于链头。验证者还可能再次遇到已执行过的职责，产生拒签或等待。

### 2.4 为什么回拨 3 小时比回拨 30 秒严重

对于刚启动不久的网络，回拨 3 小时可能把本机时间推到创世时间以前。此时不能像正常运行阶段那样得到一个有效当前 slot。此前实验中的异常涉及这种边界，以及服务对无有效 slot 的处理。

对于已运行很久的链，回拨 3 小时未必早于创世，但仍会让本机 slot 大幅落后于链头和签名记录。两者不能混为同一种故障，也不能把所有停块都称为进程崩溃；是否退出应看具体服务日志和进程状态。

## 3. Clique PoA：按高度轮流签名，时间约束何时能出块

### 3.1 它没有 PoS 那种按墙钟计算的 slot

本实验有 3 个授权签名者和 1 个观察节点，周期为 15 秒。签名者按排序后的账户列表及区块高度确定轮次。轮到的签名者所出块权重为 2，其他签名者可以在额外随机等待后出权重为 1 的块。

这里的 difficulty 是链权重，不是需要大量哈希计算的 PoW 难度。三个签名者时，最近签名限制阻止同一人连续签相邻两块。节点需要其他签名者接续，单个签名者不能无限独自推进。

机制见 [EIP-225](https://eips.ethereum.org/EIPS/eip-225)。区块高度始终按父块加一，时间变化不会直接产生跳跃的区块编号。

### 3.2 当前时间如何控制下一块

Geth v1.10.26 的 Clique `Prepare()` 等价于：

```text
候选时间戳 = max(父块时间戳 + 15 秒，本机当前时间)
```

接收方还要求：

```text
新区块时间戳 >= 父块时间戳 + 15 秒
新区块时间戳 <= 接收方本机当前时间
```

`Seal()` 根据候选时间戳减去当前时间，算出一个等待时长；非轮次节点再加随机等待，然后通过 `time.After(delay)` 等待发布。该版本在发布等待之前已经完成签名。

源码见 [clique.go](https://github.com/ethereum/go-ethereum/blob/v1.10.26/consensus/clique/clique.go) 的 `Prepare()`、`Seal()`、`verifyHeader()` 和 `verifyCascadingFields()`；高度构造见 [worker.go](https://github.com/ethereum/go-ethereum/blob/v1.10.26/miner/worker.go)。

### 3.3 回拨：链上的父块时间不会跟着回拨

假设高度 100 的时间戳为 `12:00:00`，本机也为 `12:00:00`。下一块 101 至少要标记为 `12:00:15`。

回拨到 `11:59:30` 后，下一块仍至少是 `12:00:15`，相对新时钟约需等 45 秒。回拨 3 小时则可能需要等待约 3 小时加一个周期。具体剩余等待受在途任务和调时落点影响。

所以，“调慢会使下一块等待变长”这个理解正确；“不恢复就不会有任何影响”不正确。即使所有节点一起调慢，历史区块仍在未来，出块会暂停。等墙钟重新赶上且客户端正常调度后，协议时间条件才重新允许推进。

恢复实时时钟也不保证已有等待立刻消失。本次 3 小时回拨实验中，恢复后观察 300 秒仍未持续出块。源码中的 `worker.newWorkLoop()` 在没有新交易时跳过周期重提交，本例也没有交易负载；已有长等待可能没有因恢复墙钟而立即重算。这一解释与源码和现象相符，**尚未逐线程追踪，不能认定某个等待任务是唯一原因**。

### 3.4 调快：可以接着出块，但写入了未来的历史

所有节点一起从 `12:00:00` 调到 `15:00:00`，新构造的下一块可以是：

```text
高度 101，时间戳 15:00:00
高度 102，时间戳 15:00:15
```

相对所有节点的新时钟，这些时间并非未来，因此时间条件允许继续出块。已有任务可能使实际第一个区块不同于此简化例子。

如果一直保持这个偏移，后续可以继续按高度轮次运行，但不能说毫无影响：区块时间戳已经改变，依赖时间的合约和应用也会受到影响。

如果在父块时间达到 `15:02:00` 后恢复到 `12:02:00`，下一块至少要是 `15:02:15`，接收方却认为它在未来。**恢复系统时间没有恢复区块历史**，因此又会暂停。

## 4. Monero PoW：挖出有效哈希、时间戳合法、历史调整难度是三件事

### 4.1 本轮确实使用自动难度

最终复测使用 Monero v0.18.3.3，新建 testnet，一个单线程矿工和一个同步节点，均未传 `--fixed-difficulty`。每组先预热到至少高度 65，再做正式调时；本次短链协议阶段的目标出块间隔为 60 秒，不能当成当前 Monero 主网参数。

早期对照使用固定难度 50；本节以随后完成的自动难度复测为依据。两组实验的参数和结果分别保留在本文第 5 节与附录中。

### 4.2 下一块难度怎么算：先认识难度、工作量与两种时间

**难度与时间有关，但公式用的是已接受区块里的历史时间戳，不是正在流逝的本机当前时间。** 要理解这个区别，需要把计算过程拆开。

#### 4.2.1 难度不是等待秒数，而是找到有效哈希的困难程度

矿工不断改变候选块中的 nonce 等数据，计算 PoW 哈希，直到哈希满足由难度确定的条件。难度越大，满足条件的哈希越少，平均需要尝试的次数越多。

可以近似理解为：难度为 `D` 时，平均需要约 `D` 次哈希尝试找到一个有效结果。因此，若总有效算力为每秒 `H` 次尝试：

```text
预期出块间隔 ≈ D / H 秒
```

例如：

| 难度 D | 算力 H | 预期出块间隔 |
| --- | --- | --- |
| 6000 | 100 次/秒 | 60 秒 |
| 12000 | 100 次/秒 | 120 秒 |
| 3000 | 100 次/秒 | 30 秒 |

这是统计期望，不是必须等待的计时器。某块可能很快找到，也可能远超预期才找到。改变墙钟不会让每个实际秒内的哈希尝试突然增加。

#### 4.2.2 为什么需要自动调难度

协议希望长期平均出块间隔接近目标 `T`。本实验的短 testnet 链使用 `T = 60 秒`。

但全网算力会变化，协议也无法直接测量每个矿工每秒计算了多少次哈希。因此它通过历史估算：这些区块代表了多少工作量，链上记录显示用了多长时间？

```text
估计历史算力 = 历史工作量 / 历史时间跨度
下一块难度 ≈ 估计历史算力 × 目标出块间隔
```

例如，历史估算算力为 `100 次/秒`，希望下一块平均用 `60 秒`，就把难度设为约 `6000`。若算力翻倍且历史中出块变快，估计值会逐渐上升，难度也随之提高。

#### 4.2.3 “历史工作量”如何得到

节点不知道矿工实际失败了多少次，也不会接收矿工报告的尝试次数。它用每个已接受区块的难度作为该块的工作量权重，再累加成累计难度：

```text
累计难度 C[h] = C[h−1] + 第 h 块的难度 D[h]
```

这里的工作量是共识使用的统计权重，不是实际测得的 CPU 运算次数。一个难度 6000 的块即使第一次尝试就碰巧找到，仍增加 6000 的累计难度。

假设选取的短历史如下，每个块难度都是 6000，时间戳按高度递增：

| 高度 | 区块时间戳 | 本块难度 | 累计难度 |
| --- | --- | --- | --- |
| 100 | 12:00:00 | 6000 | 100000 |
| 101 | 12:01:00 | 6000 | 106000 |
| 102 | 12:02:00 | 6000 | 112000 |
| 103 | 12:03:00 | 6000 | 118000 |
| 104 | 12:04:00 | 6000 | 124000 |

从高度 100 到 104，跨过四个出块间隔：

```text
工作量差 W = 124000 − 100000 = 24000
时间跨度 S = 12:04:00 − 12:00:00 = 240 秒
估计历史算力 = 24000 / 240 = 100 次/秒
```

注意这里用累计难度的差，所以对应的是后面四个块的工作量，而不是把表中五个难度都再加一次。

#### 4.2.4 用历史算下一块难度

该版本算法在选取历史、处理窗口和裁剪后，计算：

```text
D_next = ceil(W × T / S)
```

`ceil` 表示向上取整。时间跨度为零时，源码用 1 秒作为分母；历史样本不足两个时返回难度 1。

代入上面的例子：

```text
D_next = ceil(24000 × 60 / 240) = 6000
```

历史每块平均一分钟，已经达到目标，所以新难度保持不变。对比同样的历史工作量、不同的历史时间跨度：

| 已接受历史中的表现 | W | S | 算出的下一块难度 |
| --- | --- | --- | --- |
| 四个间隔平均 60 秒 | 24000 | 240 秒 | 6000 |
| 四个间隔平均 30 秒，出块偏快 | 24000 | 120 秒 | 12000，变难 |
| 四个间隔平均 120 秒，出块偏慢 | 24000 | 480 秒 | 3000，变容易 |

所以，“时间间隔变长会使难度下降”这个方向是对的，关键在于：**这个较长间隔必须体现在用于计算的已接受区块时间戳里。**

#### 4.2.5 为什么只等着不出块，难度不会自己下降

假设链头停在高度 104，时间戳为 `12:04:00`，历史算出的下一块难度为 6000。

```text
本机时间到了 12:05：历史仍是同一批，下一块难度仍为 6000
本机时间到了 13:05：历史仍是同一批，下一块难度仍为 6000
直接调到 15:04：历史仍是同一批，下一块难度仍为 6000
```

算法的分母不是“当前时间减去某个历史块时间”，而是“选取的历史区块时间戳之差”。链头不变，历史输入就不变。仅仅刷新 RPC 或重新请求候选模板，不会因为墙钟走了很久而得到更低难度。

源码还按链头哈希缓存下一块难度，与这个行为一致：链头未变化时可以复用结果，而无需根据当前日期重算。

这也意味着，如果算力骤降得很厉害，可能需要很久才能按旧难度挖出下一块；不能指望这里存在一个“太久没出块就按当前时间紧急降难度”的机制。

#### 4.2.6 为什么必须先按旧难度出一个块，之后才降难度

矿工和其他节点都根据父链历史算出下一个块应该满足的难度。不能先把候选块的时间戳设到三小时后，再拿这个尚未接受的块替自己降低难度。

沿用上例，当前链头是 104：

1. 历史已经决定 105 号块必须满足难度 6000。
2. 所有节点一起调快三小时，矿工给 105 的候选模板填写新的时间戳。
3. 矿工仍需按难度 6000 找到有效 PoW，其他节点也按父链计算出的要求验证它。
4. 如果 PoW 和时间戳等检查都通过，105 才成为已接受历史。
5. 节点计算 106 的难度时，才有机会把 105 的较大时间戳纳入历史，从而扩大时间跨度、降低后续难度。

本轮实测恰好展示了这个先后顺序：

| 区块高度 | 与父块时间戳的差 | 本块使用的难度 | 接受后计算的下一块难度 |
| --- | --- | --- | --- |
| 68 | 5 秒 | 6583 | 6669 |
| 69 | 10819 秒 | **6669** | **1902** |
| 70 | 20 秒 | **1902** | 1907 |

69 号块的时间戳已经跳到调快后的时间，但它仍使用旧难度 6669；69 被接受后，70 才使用新难度 1902。这里不需要真实等待三小时：算法看到的是区块记录上的时间差，无法仅凭这个差区分真实慢出块与全局时钟跳变。

#### 4.2.7 实际不是只看最后两块，还有历史窗口

前面的五块例子用于说明公式。本版本真实算法会：

1. 收集最多 735 个非创世历史区块的时间戳和累计难度，顺序按高度排列。
2. 若超过 720 个，保留这批历史中较早的 720 个。因此历史充足时，最近 15 块暂不参与计算，形成滞后。
3. 对保留的时间戳排序。样本超过 600 个时，取中间 600 个时间戳作为跨度边界；满 720 个时相当于两端各裁掉 60 个。
4. 用源码中相应边界索引的累计难度差作为 `W`，用时间戳边界之差作为 `S`，代入公式。

精确复算时还需注意：源码排序的是时间戳数组，累计难度数组仍保持高度顺序；不能自行把累计难度也按时间戳重新排序。

本轮链高只有几十，历史不足 600 个，没有触发上述裁剪，也没有形成满窗口的 15 块滞后。因此新时间戳在本轮很快进入计算。对于成熟长链，一个突变时间戳可能先被滞后排除，再被边界裁剪削弱，不能保证接受一块后就立即大幅降难度。

本轮完整区块头重算的三个快照为：

```text
调快前：ceil(450238 × 60 / 3941)  = 6855
保持中：ceil(488383 × 60 / 15113) = 1939
恢复后：ceil(509966 × 60 / 15295) = 2001
```

每项与各自链头的 RPC 报告一致。这三个快照处于不同高度，不是前表中连续三个块的难度；它们用于验证实际算法确实使用了历史工作量和时间跨度。

#### 4.2.8 时间到底通过哪些路径影响 Monero

| 时间数据 | 谁提供 | 用在哪里 | 仅修改当前系统时间会怎样 |
| --- | --- | --- | --- |
| 本机当前时间 | 操作系统实时时钟 | 创建候选时间戳、判断区块是否超过未来上限 | 立即改变后续读时结果 |
| 历史区块时间戳 | 已接受的链上区块 | 历史跨度、下一块难度和中位数下限 | 旧值不变，需接受新块才可能改变历史输入 |
| 真实经过时间 | 实际计算持续时间 | 矿工在这段时间内能做多少哈希尝试 | 本次墙钟跳变不会直接增加算力 |

因此，Monero 与时间当然有关系，但关系分为两条：**当前墙钟影响候选块及其合法性；历史时间戳影响下一块难度。** 前者改变后，只有合法新区块被接受并进入计算历史，才可能传导到后者。

下面的时间戳检查解释了另一半问题：为什么矿工明明还在计算，甚至已经找到满足难度的哈希，链却仍然不增长。

源码见 [get_difficulty_for_next_block()](https://github.com/monero-project/monero/blob/v0.18.3.3/src/cryptonote_core/blockchain.cpp#L852)、[next_difficulty()](https://github.com/monero-project/monero/blob/v0.18.3.3/src/cryptonote_basic/difficulty.cpp#L203) 和 [cryptonote_config.h](https://github.com/monero-project/monero/blob/v0.18.3.3/src/cryptonote_config.h)。

### 4.3 难度再低，也绕不过时间戳检查

本版本还独立检查：

```text
区块时间戳 >= 最近 60 个已接受区块时间戳的中位数
区块时间戳 <= 本机当前时间 + 7200 秒
```

高度不足 60 时不执行完整的中位数检查，所以本轮先预热超过 60。创建新模板时通常先取 `time(NULL)`，必要时按中位数下限调整；接收区块时仍需通过时间检查。

相关源码见 [blockchain.cpp](https://github.com/monero-project/monero/blob/v0.18.3.3/src/cryptonote_core/blockchain.cpp) 的 `create_block_template()`、`check_block_timestamp()`。

### 4.4 回拨 3 小时：上下限发生冲突，哈希工作无法变成合法区块

旧链历史仍接近 `12:00`，本机却变成 `09:00`。允许的未来上限变成约 `11:00`，而最近 60 块中位数可能接近 `12:00`：

```text
候选时间戳至少接近 12:00
候选时间戳最多只能到 11:00
不存在同时满足要求的时间戳
```

本轮偏移快照中，下限比上限高约 1545 秒；原始矿工日志直接出现：

```text
Timestamp of block ... bigger than local time + 2 hours
```

矿工仍找到候选哈希，但区块被时间规则拒绝。矿工及同步节点高度均停在 68，下一块难度保持 8799：

```text
ceil(595505 × 60 / 4061) = 8799
```

基线和回拨快照的链头、历史工作量及时间跨度完全相同，所以难度也相同。这说明当前墙钟变了，不等于难度计算历史变了。

恢复时钟后，上下限冲突解除，矿工和同步节点继续到 70。完整因果链是：

```text
内核回拨 → 当前时间降低 → 允许的未来上限降低
→ 与不变的历史中位数冲突 → 找到的候选块被拒绝
→ 链头不变 → 自动难度输入不变
```

### 4.5 调快 3 小时后恢复：本轮是未来候选模板，不能归因于中位数冲突

保持调快期间，两节点随新时钟接受区块，难度也在新历史进入后下降。恢复到正常时间时，高度已达到 86，但矿工继续提交时间戳为 `1793404354` 的未来候选块，被两小时未来限制拒绝。恢复后 300 秒内两者均停在 86，下一块难度为 2001。

**这一次中位数并没有使所有可能的时间戳都不合法。** 恢复快照中，最近 60 块只有 18 块超过本机时间加两小时，中位数仍在允许区间内。需要区分：

| 情况 | 协议是否存在合法的候选时间戳 | 停块原因 |
| --- | --- | --- |
| 历史中位数高于当前时间加两小时 | 不存在 | 时间上下限冲突 |
| 本轮调快 3 小时后恢复 | 存在 | 实际提交的候选模板仍携带未来时间戳 |

源码提供了一个与现象相符的解释：`create_block_template()` 在缓存有效且父块等条件未变化时复用模板，仅当当前时间更大时上调缓存时间戳。墙钟回退不会在这个分支主动下调时间戳。

因此，“周期性请求模板”也不必然意味着得到一个按新墙钟重建的模板。如果仍命中缓存，可能继续拿到未来时间戳。此处源码支持这种可能，但本轮没有逐次追踪全部模板刷新、缓存及计时器路径，不能把其中某一条路径称为已证明的唯一根因。

如果调快期间产生足够多未来时间戳的块，中位数本身也可能落到允许上限以外；那又会形成上一节那种协议上下限冲突。早期固定难度实验与本轮自动难度实验的出块数量不同，不能照搬同一个停块解释。

### 4.6 30 秒为什么温和得多

30 秒远小于两小时未来容忍窗口，通常不会立即制造上述上下限冲突。但中位数、候选时间戳、模板和调度仍可能受到影响，不能理解成完全没有影响。

本轮 ±30 秒的自动难度实验中，保持阶段和恢复阶段，矿工与同步节点都继续推进，没有观察到持续停高。这是本次配置下的结果，不是所有短时偏移的保证。

## 5. 四组 PoA / 自动难度 Monero 的实测汇总

每组新建链，先预热，再执行 300 秒基线、300 秒保持偏移、300 秒恢复观察，约每 10 秒采样。下表取各阶段有效采样的首末高度；阶段边界可能还有其他区块，不能据此精确计算瞬时吞吐量。PoA 取观察节点，Monero 两节点的表中高度一致。

| 调时 | PoA 保持期间 | PoA 恢复后 | Monero 保持期间 | Monero 恢复后 |
| --- | --- | --- | --- | --- |
| −30 秒 | 304 → 322 | 324 → 344 | 69 → 73 | 73 → 81 |
| +30 秒 | 230 → 249 | 249 → 268 | 66 → 72 | 72 → 80 |
| −3 小时 | 277 → 277 | 277 → 277 | 68 → 68 | 68 → 70 |
| +3 小时 | 284 → 304 | 305 → 305 | 69 → 86 | 86 → 86 |

大幅跳变时，PoA 个别签名者比观察节点高一个块：回拨场景有签名者在 278，调快后恢复有签名者在 306。这些局部高度不代表网络已经持续恢复出块。

四组正式采样中，六个客户端的 PID 未变、RPC 采样错误为零。也就是说，这里观察到的是停块或拒块，并非客户端进程退出。Monero 的原始日志还能证明矿工继续找到并提交被拒绝的候选块；仅凭 mining 状态或哈希率数字本身，不能证明有区块被接受。

PoS 是此前单独进行的实验，不能与本表当成同一组 300 秒对照。自动难度四组均已核对偏移保持和时间恢复：每组正式采样中六个客户端 PID 未变、RPC 采样错误为零，实际启动参数均未使用固定难度，完整区块头重算的难度与 RPC 一致。结束后系统时间和原校时设置已恢复。

## 6. 如果一直保持偏移，不恢复，会怎样

以下假设全部节点一起改变时间，并持续以正常速度走时，不再执行恢复操作。

| 操作 | Ethereum PoS | Clique PoA | Monero PoW（自动难度） |
| --- | --- | --- | --- |
| 调快 30 秒 | 跳过约 2～3 个 slot，通常可继续新职责与出块 | 时间戳前移，时间规则允许继续出块 | 可继续挖矿，新时间戳进入所选历史后影响后续难度 |
| 调慢 30 秒 | 暂时回到已处理的 slot，可能拒绝重复职责；赶上原进度后有恢复机会 | 等待墙钟赶上父块时间加周期后，可以继续出块 | 本轮保持期间继续推进，未观察到持续停高 |
| 调快 3 小时 | slot 前移约 900，本轮短期保持期间能出块；跨 epoch 状态与最终性仍可能受到影响 | 时间戳跳到新时间，本轮保持期间继续出块，高度连续 | 先按旧难度挖出新块，较长时间间隔进入所选历史后影响后续难度；本轮难度下降并继续出块 |
| 调慢 3 小时 | 当前 slot 大幅落后于链头或创世；可能等待、拒绝职责或报错。若服务已退出，仅等待不会将它自动重启 | 父块位于未来，通常需等待约 3 小时加剩余出块间隔；实际恢复还受已有任务影响 | 可能因两小时未来上限与历史中位数冲突而拒块；墙钟前进使合法区间重新出现后，才有恢复机会，不一定要等满 3 小时 |

调快且不恢复，可以避免“恢复时再次回拨”造成的第二轮问题，但时间戳、slot、应用及共识状态仍已发生变化。调慢且不恢复，需要经历等待或异常阶段，因为已接受的区块和签名记录没有跟着倒退。

表中长期恢复预期来自协议和源码分析。本次每场景只进行有限窗口的观察，没有验证数小时后的自动恢复、永久偏移下的最终性、重组或应用行为。“恢复后 300 秒没出块”也不等于永久无法恢复。

如果只调部分节点，其他节点的时间不变，问题会不同：PoS 对当前职责的判断会分歧，PoA 可能拒绝未来区块，Monero 可能触发未来上限。本次全局调时不覆盖这种局部时钟偏差。

## 7. 如何理解这三个实验的共同点与区别

三种客户端都从操作系统获得时间，但时间进入共识的位置不同：

| 机制 | 当前时间首先影响什么 | 调时后不会自动回退的内容 |
| --- | --- | --- |
| PoS | 当前 slot、职责与消息时效 | 已知链头、已执行职责和签名保护记录 |
| Clique PoA | 候选时间戳、发布等待和未来块检查 | 父块时间戳、已签任务和已有等待 |
| Monero PoW | 候选时间戳和未来块上限 | 已接受时间戳历史、历史工作量和缓存模板 |

真正需要理解的是：**时钟是一份状态，区块历史和客户端运行状态是另外几份状态。调时只直接改变第一份，却会通过读时、校验和调度改变后续行为。恢复第一份，不会自动撤销其他状态中已经发生的变化。**

这也解释了为什么修改实时时钟不能直接作为“加速区块链仿真”的办法：我们让共识突然看到另一段日期，没有让计算、网络传输、单调计时器和已有链状态同步按同一倍率前进。

## 附录：早期固定难度对照

最初的 PoA / Monero 对照使用相同客户端版本。Monero 固定难度为 50，每组先预热到至少高度 65，再记录 90 秒基线、120 秒偏移保持和 120 秒恢复观察。固定难度绕过自动难度计算，不能据此判断自动难度是否下降。

| 操作 | PoA 保持期间 / 恢复后 | Monero 保持期间 / 恢复后 |
| --- | --- | --- |
| 调慢 30 秒 | 短暂停顿后继续 / 继续 | 矿工继续，同步节点断连停高 / 同步节点未追上 |
| 调快 30 秒 | 继续 / 短暂停顿后继续 | 继续且同步 / 同步节点在恢复回拨后断连，矿工继续 |
| 调慢 3 小时 | 无持续推进 / 窗口内未恢复 | 候选块被未来时间检查拒绝 / 恢复出块与同步 |
| 调快 3 小时 | 继续 / 窗口内停止推进 | 继续且同步 / 候选块被拒绝，窗口内未恢复 |

短回拨时，同步节点出现缺失父块及对等对象请求不匹配的日志；完整 P2P 内部触发路径未定位。后续自动难度实验没有复现相同短回拨停高现象，不能将两轮差异简单归因于某个未验证的内部机制。

固定难度调快 3 小时期间出块较多；恢复后最近 60 块均超过本机未来两小时，形成时间戳上下限冲突。自动难度复测仅有 18/60 块超过未来上限，中位数仍允许合法时间戳，但实际候选模板保留未来时间戳。因此，两轮恢复后的停块现象相似，直接原因不同。
